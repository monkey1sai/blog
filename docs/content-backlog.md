# 下一批最值得補的內容

目標：讓讀者看懂「作品怎麼用、竣傑做了哪些判斷、結果如何驗證」，而不是增加沒有證據的篇幅。以下是待提供的素材清單，不是已完成成果或發布承諾。不會自動出現在正式網站。

## 先補這三件，每件只需要一小組真實材料

### 1. 常山龍膽：一次完整的遊玩與判斷

- 提供：30–60 秒真實遊玩錄影，包含出陣、普通攻擊、龍膽、暫停或重試；註明版本、日期、裝置與操作方式。
- 補一句：「哪個地方原本不滿意？我要求怎麼改？最後用什麼判斷能不能留下？」
- 若要比較修改前後，提供同一場景與操作的兩份真實素材；沒有可比素材就只介紹目前版本。
- 放置：案例的「我的選擇」與「成果與證據」。不要把一次遊玩當成全裝置、全難度驗收。

### 2. Codex Jev：一個去識別化的輸入到決策案例

- 提供：任務背景、候選資源、Jev 建議、Codex 最後採取或拒絕的決定，以及一個退回補資料的例子。
- 隱去：憑證、內部路徑、私人專案內容與第三方個資。
- 補一句：「這次建議幫我看到什麼？哪個判斷仍必須由我或確定性規則處理？」
- 放置：案例的「AI 協作」。在做過同條件比較前，不寫更快、更省或品質提升。
- 若要補比較：同一任務與版本、有／無 Jev 的條件、耗時與成本記錄、評分標準、失敗案例都一起保留。

### 3. AERIS：一張真正的畫面與一條可追查的紀錄

- 提供：本機畫面截圖、版本與日期、從 trace 到 claim／evidence 的操作順序。
- 明確標註資料是 fixture／示範資料還是真實流程；只用可公開且已去識別化的資料。
- 補一句：「看到這條紀錄後，我能回答哪個以前回答不了的問題？」
- 放置：案例的「成果與證據」。保留目前本機 MVP、真實 Google 帳號驗收未完成的界線，概念封面不能代替產品畫面。

## 再補兩種能讓人認識你的短篇

1. 一次沒有採用 AI 建議的決定：原建議 → 你不同意的原因 → 採用方案 → 驗證結果。約 400–800 字即可，連回原案例，不需要另造成功故事。
2. 一次卡關或失敗：預期 → 實際觀察 → 排除哪些原因 → 現在仍不知道什麼。附一小段可公開的證據與日期。

有真正內容才發布文章；不要為了填滿文章區加入空白預告。沒有新驗證，就不要更新成果日期或把舊數字寫成最新數字。

## 發布前核對

- 圖像、錄影、文字是可公開的，並有清楚的素材來源與使用權。
- 明確交代人的判斷、AI 協作和既有工具，沒有新增無法證實的經歷或成就。
- 測試數字保留日期、環境、通過／略過／失敗與範圍。
- Demo、原始碼、資料與下一篇連結都可開啟；手機不能操作時，在點出去前說明。
- 效益以使用者回饋或可重現比較支持，沒有證據時只寫觀察與限制。
